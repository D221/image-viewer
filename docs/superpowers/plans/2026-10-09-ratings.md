# Ratings and Tags Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 0–5 star rating, a culling flag, and free-form tags per image, stored as XMP sidecars, shown in the left pane and the grid, and navigable from the filter box.

**Architecture:** A new `src/ratings.rs` holds the sidecar model and a **surgical** XMP editor — it reads and rewrites only `xmp:Rating`, `xmp:Label` and our keyword element, and preserves every other byte of an existing sidecar. `lib.rs` re-exports the public surface so the app and tests use one path. All storage logic is pure over bytes and paths, so it is testable without a GUI.

**Tech Stack:** Rust 2021, hand-written XML attribute editing (no new dependency — see Global Constraints), existing `image_viewer::{looks_like_supported_image, is_archive_path}`.

**Spec:** `docs/superpowers/specs/2026-10-09-undo-and-ratings-design.md` — read §2 (Ratings and tags) before starting.

## Global Constraints

- **No new dependency.** XMP is RDF/XML, and the plan deliberately does *not* add an XML or XMP crate: parsing one properly and preserving foreign packets is the hard part, and a general parser is how you end up rewriting (and dropping) another tool's data. This is a targeted attribute editor. Do not "improve" it into a parser.
- **Never rewrite a sidecar wholesale.** If a sidecar exists, edit only the target attribute's bytes in place and leave everything else untouched — a Camera Raw packet, a Lightroom histogram or a Dublin Core block must survive a round trip byte-for-byte. Dropping another tool's metadata is worse than not having ratings.
- **Atomic write, always:** `.tmp` then rename. A partial sidecar must never be read back as a rating. Same rule and same reason as the thumbnail cache's `IEND` check.
- **Ratings are not undoable** (spec §1/§2). `Ctrl+Z` does not touch them.
- **No ratings inside archives.** `vol1.cbz/page003.jpg.xmp` has nowhere to go; refuse visibly rather than write somewhere it will not be found.
- **Every bare letter must be added to `BARE_LETTERS`** in `tests/keybindings.rs` with the reason. This is a genuine extension of that rule (a rating *writes* a file), so the entry must say so explicitly.
- **Full suite before every commit:** `cargo test --no-fail-fast` — 27 targets.
- **Mutation-check every source scan.**

## Review Focus

Five input/failure classes the spec implies, most likely to bite first.

1. **A sidecar written by Lightroom, then a rating set here.** Expected: `xmp:Rating` updated, every other packet byte-identical. This is the interoperability claim, and a whole-file rewrite fails it.
2. **A sidecar with no `xmp:Rating` element at all** (written by Bridge, say). Expected: the attribute is *inserted* into the right element, not dropped, and the file stays parseable.
3. **The image is inside an archive.** Expected: rating refused with a message naming the reason — not silently written to `%TEMP%` and lost on exit.
4. **Two files sharing a stem** (`photo.jpg` and `photo.png` in one folder). Expected: two distinct sidecars (`photo.jpg.xmp`, `photo.png.xmp`), each holding its own rating, neither overwriting the other.
5. **A truncated or hand-edited sidecar.** Expected: an error naming the file, and the **image** still opens and rates fine. A broken sidecar must never make a photo unopenable.

- [ ] **Step 3: Implement `merge` as a byte-level attribute editor**

`parse(&str) -> Ratings`:
- `xmp:Rating="N"` → `stars`, clamped to `0..=5`, else 0.
- `xmp:Label="Pick"` → `flag = true`; `xmp:Label="Reject"` → `flag = false`.
  **`Second` maps to `false` and is preserved on write** — it is a third state
  this app does not use, and rewriting it to `Reject` would destroy a judgement
  another tool made. (Implement as `Option<String>` internally so an absent
  `Label` and a `Second` are distinguishable; both write back as-is unless the
  flag is toggled.)
- Keywords: our own element, `iviewer:Keywords` in a
  `xmlns:iviewer="https://image-viewer.local/ns/1.0/"` namespace, as
  `<rdf:Bag><rdf:li>tag</rdf:li></rdf:Bag>`. Namespaced under our own URI so it
  cannot collide with another tool's element.
- A string with no `<x:xmpmeta` → `Err`.

`merge(existing, new) -> String` — the part that matters:
1. If `existing` is empty, emit a minimal valid sidecar containing only our
   attributes. This is the only case where anything is constructed from scratch.
2. Otherwise, **string-surgery on `existing`**, never a re-serialise:
   - `xmp:Rating`: if present, replace the value between the quotes in place; if
     absent, insert ` xmp:Rating="N"` immediately after the first
     `<rdf:Description` tag's attribute list (before its `/>` or `>`).
   - `xmp:Label`: same treatment, but **only when the caller changed the flag**.
   - Keywords: replace the whole `<iviewer:Keywords>…</iviewer:Keywords>` span if
     present, else insert the element before `</rdf:RDF>`. It is ours, so
     replacing the span wholesale is safe — unlike `xmp:Rating`, which is shared.
3. Return the result. Every byte outside those spans is the input's.

Then `write`: `merge` → `fs::write(tmp)` → `fs::rename(tmp, side)`.
